## 1. 角色和不可变规则

| 角色     | 负责什么                                                       | 权限边界                                                                 |
| -------- | -------------------------------------------------------------- | ------------------------------------------------------------------------ |
| 顾客     | 浏览、选择项目/技师/店铺、提交预约、同意改派、验收、评价、售后 | 只访问本人地址、预约、消息和工单                                         |
| 店铺     | 自主定价、受理、安排人员、履约跟进、取消退款、经营和财务       | 只经营会话所属店铺；不能代技师授权肖像，不能代顾客同意换人               |
| 技师     | 在有效绑定内确认任务、出发、到达、服务、异常报告和店内事实协作 | 仅本人合法任务；不能接受服务合同、定价、转单或决定退款；没有独立提现钱包 |
| 平台员工 | 资质/内容审核、安全、投诉调查、订单监控和账务治理              | 按岗位、业务组和具体权限授权；普通治理不代替店铺常规接单或退款           |

共同规则：

1. 一笔订单只属于一个店铺及其经营主体；后端解析归属，客户端不能指定另一个商户。换店需要结束原预约、重新确认新交易。
2. 顾客选中的人员和实际获派人员分别保存。指定技师改变必须经顾客明确同意，不因超时或沉默推定同意。
3. 公开展示必须同时满足有效店铺、人员绑定、身份核验、肖像授权、发布和项目资格。停止展示不应抹掉既有订单及善后记录。
4. 前端展示和操作提示不是授权。每次写入都重新校验角色、资源归属、当前状态、版本和业务条件。
5. 已提交订单冻结项目名称、时长、金额、取消政策、经营主体和受理依据。店铺后续改价不改原单。
6. 一个自然人的时间占用按 `staffId` 跨店检查；在途、到达和服务事实也必须避免同时推进多笔任务。
7. 真实零值可以显示 0；读取失败或缺失用未知和重试。距离只有设备授权后的服务区域中心直线估计，不冒充技师实时位置。

## 2. 顾客从三个维度进入同一预约流程

| 入口   | 用户先选什么         | 接入预约时的规则                                         |
| ------ | -------------------- | -------------------------------------------------------- |
| 选项目 | 项目、时长和所属店铺 | 重新读取当前供给；再选择本店合格技师或由店铺安排         |
| 选技师 | 有有效店铺归属的技师 | 只能选择其已获准的本店项目；默认指名，费用包含本店指名费 |
| 选店铺 | 店铺及其菜单         | 默认店铺安排，不收指名费；明确选人后才切换指名           |

首页、目录、详情、发现内容、收藏和再次预约都汇入现有预约链路。跨项目/店铺/技师导航可以保留地区、语言、预约方式，不能复用旧报价、hold、支付凭据或不兼容时段。再次预约也按当前资格、价格和时段重新确认。

当前首页展示上限为 9 个精选项目、6 名合格技师、4 家店铺。它们是上限，实际数量以真实可展示供给为准；不能为了凑数复制人员或伪造店铺。

## 3. 供给、入驻与配置

### 3.1 店铺与人员的准入链路

商户注册 → 店铺草稿/主体与三语资料/服务与材料 → 提交修订快照及条款 → 平台审核 → 通过后启用店铺。

店铺邀请 → 指定邮箱的技师个人账号领取 → 有效绑定 → 个人资料、材料、可承接项目 → 本人对确切版本授权肖像 → 店铺确认公开资料 → 平台审核 → 符合条件后发布。

退回整改、拒绝、暂停、到期和解绑都保留历史；解绑立即撤回原店工作访问与公开展示，存量订单由原店改派或取消善后。个人技师不能绕过店铺直接售卖服务。当前开放的类目为 `RELAXATION`，受监管类目不能靠改名绕过审核。

### 3.2 店铺配置的作用时间

| 配置                       | 新预约                                         | 已提交订单                                         |
| -------------------------- | ---------------------------------------------- | -------------------------------------------------- |
| 服务价格、交通费、有效优惠 | 按当前项目版本报价                             | 保留订单报价；优惠自然结束不重算原单               |
| 指名费、取消政策           | 按当前店铺版本报价并确认                       | 按冻结政策计算，改派免除原指名费                   |
| 上门规则 / 到店门店设置    | 各自只让本模式未提交的报价失效                 | 互不影响；改上门指名费不会让到店报价报错，反之亦然 |
| 时段附加费                 | 按开始时间（JST）落入的店铺时段报价，单列一行  | 冻结在报价中；修改或删除附加费不改原单             |
| 地区交通费                 | 按顾客地址所在地区报价；免交通费项目保持 0     | 冻结在报价中；改表不改原单                         |
| 自动受理授权               | 校验项目、人员、区域、JST 时段、金额、每日额度 | 保存当时的决策依据；不能靠改设置覆盖原单           |
| 休息/请假/不可约时间       | 与时段和缓冲占用冲突则不可预约                 | 有冲突时拒绝新增时间块，不能静默挤掉订单           |
| 资质、绑定、公开权限       | 不满足即停止新供给                             | 留存原交易；关键履约操作另查当前资格并由店铺善后   |

### 3.3 价格口径

当前最终报价 = 生效服务价格 + 交通费 + 指名费 + 时段附加费；店铺安排的指名费为 0，时段附加费照常收取。展示比较价仅来自符合规则的真实优惠，不制造划线价。报价版本改变或未提交报价过期时，需要重新选择和确认。

时段附加费（PRD 35.1、49 章、CP-06）：

- 店铺最多配置 2 段日本时间区间（15 分钟单位，可跨午夜），每段 100–20,000 日元，不能重叠；属于「指名费与取消政策」同一版本与历史。
- 只按预约开始时间判定（含起点、不含终点），跨午夜不重复收取。指定时间预约只在店铺营业时间内开始（默认 9:00–22:00，可跨午夜或 24 小时），营业时间以外的区间主要作用于即时预约。
- 营业时间由店铺在预约规则中设置（日本时间、30 分钟单位），可约时段列表与报价校验使用同一规则，营业时间外的报价返回 `OUTSIDE_BOOKING_HOURS`。即时预约按上班状态。
- 服务端计算并写入报价 `timeSurcharge`，订单冻结。取消费、爽约费和平台服务费基数均为「总价 − 交通费」，因此包含附加费；自动受理金额门槛也按含附加费的总价判断，即时可约预览与报价一致。
- 详情页说明各段附加费；下单页选定时间后单列金额；H5 目录价格按所示最早时段计算，价格排序使用基础价。详见 [指名费、时段附加费与取消政策](SHOP_PRICING_CANCELLATION.md)。

地区交通费（PRD 49 章「以区域/距离区间预先报价」）：

- 店铺可为本店服务地区逐个设置交通费（0–20,000 日元）；表中地区替代项目交通费，未列地区使用项目交通费；项目交通费为 0 的免交通费项目在所有地区保持 0。
- 报价按顾客地址地区计算并冻结，提交时按同一规则复核；改表后旧报价需重新报价。取消费、爽约费和平台服务费基数本来就排除交通费，因此不受影响。
- 选了地区的列表、筛选、标签和排序都使用该地区金额；没有地区的卡片显示项目交通费，详情页和下单页列出店铺地区交通费表。按距离区间计价需要地址定位，未实现。

取消费和爽约费使用原订单政策、服务端时间、原服务金额和当前阶段。取消前先读取实际费用，确认时再检查费用与订单版本；跨收费档位必须重新核对。店铺原因、指定人员无法履约和符合原政策的即时到达延迟按免费取消处理。

人员差异定价、按距离区间的交通费、服务中延长加时和真实履约证据仍属于后续范围，不能仅凭界面字段视为已实现。

## 4. 下单、受理和人员确认

### 4.1 下单链路

1. 校验供给、地区、语言、项目及当前时段；登录或完成必要等级验证。下单页列出未来 14 天的可约时间（报价本身接受 30 天内），时间列表与报价使用同一套营业时间、排班、安全条件和占用规则。
2. 后端创建报价（默认有效 15 分钟）。价格和政策由后端计算，不接受客户端总价。
3. 创建结算保留 `CHECKOUT_HOLD`（默认 10 分钟），同一自然人跨店的服务和缓冲时段不能冲突；限制有效保留数与频率。
4. 填写本人服务地址。酒店需酒店名、房号与访客许可；人员的酒店限制不能被地址草稿绕过；首次深夜住宅预约有更高验证要求。
5. 取得现有模拟支付保障，核对经营主体、费用、政策和条款后提交。真实渠道接入本轮暂缓，已有保障门禁保留。
6. 创建订单和 `BOOKING_RESERVATION`，使用与内容绑定的幂等键。重复提交返回原订单，不能重复创建或重复授权。
7. 顾客主动修改未提交预约时释放原保留；已经提交的 hold 只恢复原订单。倒计时以服务端时间及单调经过时间为依据。

### 4.2 四种组合、三种受理方式

即时/指定时间 × 指名/店铺安排构成四种预约组合。

| 受理方式             | 适用                       | 店铺动作与技师动作                                                                             |
| -------------------- | -------------------------- | ---------------------------------------------------------------------------------------------- |
| `MANUAL`             | 指定时间预约               | 店铺明确受理；有人员则发任务，无人员先安排；技师再确认                                         |
| `AUTO_PREAUTHORIZED` | 指定时间及授权范围内的即时 | 在明确授权范围和额度内自动受理，技师仍需确认；范围外普通预约转人工，即时预约拒绝并提示重新选择 |
| `SOLO`               | 符合条件的单人店           | 经营者以店铺身份一键受理并确认本人工作；必须重新确认当前唯一人员的合法资格和接单条件           |

默认响应窗口：即时 5 分钟，近 24 小时预约 30 分钟，远期 240 分钟；同时受最迟确认时点约束。近时改派默认 15 分钟。具体计算以 `engine.deadline()`、配置和订单记录为准，不能用客户端倒计时延长。

技师确认后保留升级为 `CONFIRMED_BLOCK`。收到任务、店铺已受理和人员已确认是不同事实，界面不能合并成“已接单”。

## 5. 订单状态与并行轨迹

| 主状态                               | 业务含义                                     | 正常下一步及负责人                           |
| ------------------------------------ | -------------------------------------------- | -------------------------------------------- |
| `REQUESTED`                          | 已提交，待店铺受理                           | 店铺接受/拒绝，或系统超时关闭                |
| `ACCEPTED`                           | 店铺已受理，人员尚未全部确认                 | 店铺派发，合法获派技师确认                   |
| `CONFIRMED`                          | 正式安排；仍需结合任务及改派状态判断能否履约 | 已确认的技师出发；需要换人时走改派           |
| `EN_ROUTE`                           | 已出发                                       | 同一技师到达；可报告延迟                     |
| `ARRIVED`                            | 已到达                                       | 到预约开始时点后开始；无法联系顾客走爽约核实 |
| `IN_SERVICE`                         | 已开始                                       | 服务足时后提交结束，或报告异常               |
| `AWAITING_COMPLETION`                | 技师提交结束，待顾客核对验收                 | 顾客确认/异议，店铺复核，必要时平台介入      |
| `COMPLETED`                          | 顾客验收完成并按现有模拟规则扣款             | 评价、售后、账务和复购                       |
| `REJECTED` / `EXPIRED` / `CANCELLED` | 拒绝、超时、取消的终止记录                   | 不能继续履约；按实际已扣与未退余额办理售后   |

必须一起读取的独立轨迹：

- 店铺受理 `merchantAcceptance`：待处理、人工/自动受理、拒绝、超时。
- 技师任务 `staffTaskStatus`：未派发、待回应、已确认、拒绝、过期、撤回。
- 改派 `replacementConsent`：无需、待同意、同意、拒绝、过期；候选和截止时间独立保存。
- 完成验收 `completion.status`：待确认、异议、超时、支付待核验、已确认、无费用关闭。
- 支付、退款申请、投诉工单、安全事件各有独立状态。工单结案不等于退款完成，技师结束不等于顾客验收，报表中的净额也不等于真实银行到账。

## 6. 改派与无法履约

指定人员拒绝/撤回 → 原订单保留、店铺善后 → 同店合格候选及临时占用 → 顾客明确同意 → 再次校验候选和冲突 → 更新实际人员、免除原指名费 → 新技师确认任务。

顾客拒绝、改派超时或店铺取消都不能静默换人。候选撤回后等待店铺重新处理，不能通过重复提议延长原改派期限。原选定人员始终保留在订单，旧人员的敏感任务访问随获派关系变化撤回。

店铺安排可由本店更换合格人员，原 SKU 和金额不变；新人员仍需确认。跨店不能改原订单归属。

## 7. 履约、完成验收与安全

正常操作：任务确认 → 出发 → 到达 → 开始 → 足时结束 → 顾客验收。每一步检查前一步状态、当前版本、本人任务及当前资格；禁止提前开始或缩短已购买时长。服务时长来自订单快照，不能信任客户端计时。

同一人员如仍有另一笔在途、已到达或服务中任务，应先结束/取消/善后该任务，再推进下一笔现场履约；计划时段已经结束不能自动证明实际服务结束。

服务结束后由顾客核对金额并确认。结束后 72 小时内既未确认也未异议时，足时、无异议/异常且授权有效的订单视为验收并扣款一次（已向顾客三语告知）；有异议或异常、时间记录无效或支付保障失效时转复核，不自动扣款。店铺可联系、调查、请求重新确认或无费用关闭，平台查看异常并跟进；不能由店铺代替顾客点击完成。即时单到达后即可开始，指定时间预约不早于预约时间开始。

远期支付保障（PRD CP-44）：下单时只有当授权有效期覆盖服务结束后的 72 小时验收期时才立即授权，否则保存已认证支付方式，并在上门前 48 小时由后台预授权。预授权失败时订单标记支付失败，顾客须在 12 小时内（且不晚于开始前 1 小时）重新认证；期间技师不能出发，顾客取消免费。逾期未更新则免费取消并释放时段，原因 `PAYMENT_GUARANTEE_FAILED`。

安全签到、SOS、迟到和爽约是独立流程：

- 到达估计不能覆盖原承诺；即时延迟是否满足免费取消仍按冻结的原承诺和宽限计算。
- 服务超出预计结束 15 分钟发起签到，默认再等 5 分钟未回复升级；安全和一般工作事实按权限隔离。
- 爽约需订单内联系留痕、次数及等待期，店铺核实后处理，不能仅由技师标记即扣费。
- 当前安全提醒和联系记录不表示已经联系真实应急机构或外部联系人。

## 8. 售后、评价与复购

### 8.1 售后闭环

顾客原订单 → 退款申请或普通问题 → 原店回复/核实技师事实 → 全额、部分批准或拒绝 → 争议升级平台 → 调查结论 → 原店执行 → 核验与结案 → 顾客可重新申诉。

退款只能针对终止/完成订单的实际已扣未退余额，同笔订单同时最多一个待处理申请。顾客撤回不改变已退金额；再次申请重新检查当前余额。原店决定退款，平台方案发布只是治理结论，不能假装资金已经执行。

平台调查必须有事实来源、理由、版本和必要店铺陈述；退款建议与真实执行不一致时不能直接结案。店内事实协作不自动公开给顾客或平台，技师不能读取顾客私密投诉和退款余额。

### 8.2 评价、收藏与浏览记录

只有真实完成且满足已扣款条件的本人订单可评价；先审核后公开。修改重审、撤回、店铺回复和内容争议独立留痕。公开评分与评论数只统计允许公开的记录，零评价不显示虚构满分。

收藏是本人真实记录；公开被收藏数按实际有效收藏聚合。浏览记录属于当前设备范围，不应冒充跨设备完整历史。复购回到当前项目与供给，旧支付、报价和 hold 不复用。

## 9. 各端待办和异常恢复

| 端         | 优先待办                                            | 操作后应联动                           |
| ---------- | --------------------------------------------------- | -------------------------------------- |
| 顾客 H5/PC | 恢复未提交保留、改派同意、当前履约、验收、售后回复  | 原订单、费用、消息、退款余额、评价资格 |
| 店铺       | 待受理、待安排、人员拒绝、爽约待核、完成复核、售后  | 技师任务、顾客当前事项、监控、账单     |
| 技师       | 本人待确认、现场履约、安全签到、原店事实请求        | 原店安排、顾客进度、验收状态和异常记录 |
| 平台       | 资质/内容审核、安全、超时、调查、执行核验、财务差异 | 供给可见性、原店跟进和权限内必要状态   |

共同异常约定：

- 加载中、真实空数据、无权限和读取失败分别处理；目录失败不能阻断本人订单。
- 写操作有提交锁，关键交易有服务端版本/幂等校验。409 时重新核对，不能自动替用户同意新金额/新人员。
- 页面切换角色或目标记录后，旧响应不能回填；失败保留可恢复草稿，但金额、人员和操作资格必须重新读取。
- 工作台刷新/轮询和重新聚焦核对只读现状，不能偷偷执行确认、取消或退款。
- 中日英共用同一业务状态和金额口径，H5/PC 共用同一接口与权限；翻译不另造流程。
