## 2. 发现的问题（按严重程度）

### P0 — 上线前必须解决

**1. 每个请求都全表扫描且全局串行，数据量上来后不可用**

- `engine.ts:123` `run()` 在每个事务（包括只读的公开目录、可约时段查询）里先执行 `sweep()`（`engine.ts:2106`）。`sweep` 遍历全部店铺、技师、时间块、休假申请、hold（每个过期 hold 再遍历全部支付记录）和全部订单。
- `repository.ts:51` 的事务是一个进程内的全局队列；SQLite 用 `BEGIN IMMEDIATE`，PostgreSQL 用全局 advisory lock（`repository.ts:63`），读请求也排队。
- 业务查询普遍使用 `tx.list(kind)` 把整类记录读进内存再过滤（例如 `engine.ts:255` `freeStaff`、`engine.ts:295` `publicCatalog`）。
- 实测（内存 SQLite，隔离于演示库）：

| 订单数 | 公开目录单次 | 可约时段单次 | 20 个并发目录请求 |
| ------ | ------------ | ------------ | ----------------- |
| 0      | 1 ms         | 3 ms         | 27 ms             |
| 2,000  | 95 ms        | 75 ms        | 1.7 s             |
| 10,000 | 421 ms       | 367 ms       | 8.5 s             |
| 30,000 | 1,312 ms     | 1,027 ms     | 25.9 s            |

- 建议：
  1. 把 `sweep` 移出请求路径，改为后台定时任务，按到期时间索引查询（`expires_at` / `deadline` 索引），只处理到期记录。
  2. 只读请求不进入写事务、不加全局锁。
  3. 订单、hold、支付、费用账改为规范化表并建立索引（`store_id`、`customer_id`、`status`、`start_at`），按条件查询，不再 `list()` 全量。
  4. PostgreSQL 用行级锁或按技师粒度的 advisory lock 代替全局锁；busy interval 的排斥约束已经存在，可以作为最终防线。

**2. 身份与验证仍是演示实现**（已知、且有生产启动保护）

- `controller.ts:132` 任何人 `POST /v1/auth/demo` 都能以顾客、店铺、技师甚至平台管理员身份登录。`config.ts` 中的 `assertDemoRuntime` 会阻止生产模式启动，这一保护是有效的。
- 顾客验证等级固定为 1（`controller.ts:156`），L2/L3 没有真实流程；因此 `engine.ts:788` 的“首次深夜住宅上门需 L3”对演示顾客总是拦截。
- 真实 PSP、LINE、短信、邮件尚未接入；PostgreSQL 适配器从未实际运行过（README 已说明）。

### P1 — 与 PRD 不一致（规则被简化）

**3. 预授权自动受理没有规则范围**

2026-10-19 第二十九轮已补齐本地实现：项目/人员/区域/时段/金额/每日上限、授权版本与暂停、普通预约转人工、即时各步骤校验及订单决策快照。630 项测试、1514 项隔离检查通过，详见 [AUTO_ACCEPTANCE_RULES.md](AUTO_ACCEPTANCE_RULES.md)。下方为修复前的问题记录；正式授权合同和生产工程仍待接入。

- `engine.ts:818` 只要店铺 `acceptanceMode === 'AUTO_PREAUTHORIZED'` 就自动受理所有订单。PRD 第 6.2 节要求店铺限定 SKU、人员、时段、区域、单笔金额、每日上限，并可按项目暂停。

**4. 指名费、取消政策是全局配置，不是店铺配置**

2026-10-19 第三十轮已补齐店铺指名费、模板/自定义分档政策与冻结版本，联动多店总价、预算/排序、取消/爽约和改派免原指名费。657 项测试与 1514 项隔离检查通过，见 [SHOP_PRICING_CANCELLATION.md](SHOP_PRICING_CANCELLATION.md)。下方为修复前记录；按人员/SKU 的差异指名费、交通矩阵及时段附加费仍待后续实现。

- 指名费 `config.ts:13` 全平台统一 500 日元；取消政策 `config.ts:19` 全平台统一（`demo-policy-v3`）。PRD 第 35、49.4 节要求店铺自定价、从模板选择取消政策，并以版本快照写入订单。交通费为每个 SKU 一个固定值，没有按区域/距离的区间，也没有深夜等时段附加费。

**5. 取消费从“已保存支付方式”直接记为已扣款**

- `engine.ts:1810` 对 `METHOD_SAVED`（远期预约，尚未与信）的订单收取取消费时直接标记 `PAID`。接入真实 PSP 后需要走 off-session 扣款或重新授权，失败要有处理路径。

**6. 消息风控只拦截，不进入安全队列**

- `engine.ts:2013` 用一个很短的关键词正则直接拒绝消息。PRD 第 51.5 节要求：对发送方提示 + 进入安全审核队列 + 三语词库维护，并与 listing 举报、异常模式联动。

### P2 — 工程质量

**7. 控制器是一个 1,150 行的正则路由**

- `controller.ts:98` 用 `@All('*path')` 接管全部请求，再用一长串 `path.match(...)` 分发。NestJS 的模块、守卫、管道、OpenAPI 都没有用上，路由顺序依赖手工维护，权限校验分散。建议按领域拆分 Controller，并用守卫统一鉴权，由 OpenAPI 生成前端 SDK（PRD 第 42.3 节）。

**8. 公开接口返回内部字段**

- `engine.ts:337` 公开目录直接返回整个 listing（含 `staffId`、`membershipActive`、`identityVerified`、`dutyUpdatedAt`）和店铺的 `merchantId`、`plan`、`ruleVersion`、`billingBlocked`。风险不高，但应改为显式的公开 DTO。

**9. 前端样式失控（本轮已部分处理）**

- 21 个 CSS 文件约 3.3 万行，写死了 **1,103 种不同颜色**（共 1,707 处），三个文件各自重复定义 `:root` 变量，后加载的覆盖先加载的。
- 正文字体栈只有日文字体（`Arial, Hiragino, Yu Gothic, Meiryo`）。**简体中文页面里“铺、边、务、费”等日文字体没有的字，会回退到另一种更粗的字体**，所以标题出现个别字“莫名加粗”，中文还会显示成日文字形。本轮已修复，见第 3 节。

## 4. 后续建议（UI）

1. 继续合并 CSS：21 个功能样式文件中仍有大量重复和互相覆盖，建议按组件拆分（或迁移到 CSS Modules / Tailwind 令牌），每个组件只有一处样式来源。
2. 真实上线时用真实、经授权的技师照片替换插画，这是“高级感”提升最大的一步；卡片布局已为照片预留比例。
3. 为中文标题引入网页字体（如 Noto Serif SC 子集），保证没有安装宋体类字体的 Windows 用户也能看到衬线标题。
