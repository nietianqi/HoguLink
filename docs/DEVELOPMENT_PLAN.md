## 结构和技术选择

在一个工作区保留 `hogulink-web`、`hogulink-api`、`hogulink-app` 三个边界，先不创建远程仓库。Web 四角色共用 Next.js 应用与组件，通过角色路由及服务端授权隔离；API 是 NestJS 模块化单体。`packages/contracts` 是共享类型与输入校验。以 npm workspace 降低本机环境准备成本，锁文件固定依赖；与 PRD pnpm 的差异仅为包管理器。

PostgreSQL 为目标数据库，提供 Docker 与数据库排斥约束。本地未安装 PostgreSQL 时使用 Node SQLite 适配器；两者使用同一领域逻辑，写操作串行事务，hold/booking 的时间冲突再由数据库约束防守。SQLite 仅用于单机演示，不用于多实例生产。当前业务实体以类型化 JSON 文档存储，忙碌区间独立规范化；生产前按迁移计划拆分业务表、补完整外键及报表索引。

## 关键约束

- 服务器从 listing / SKU 推导商户和店铺，创建后不可改；价格、政策、法定主体冻结快照。
- 即时只允许 AUTO_PREAUTHORIZED / SOLO，必须待机且有紧急联系人。
- L1 才能 hold；有效支付保障和地址才可达到 L2 并提交。演示认证与演示支付只能在本机 demo 模式工作，生产模式启动失败。
- hold 有 TTL、并发数量和频率限制；创建预约必须有 Idempotency-Key，键与客户、操作及输入绑定。
- BOOKING_RESERVATION 和 CONFIRMED_BLOCK 阶段持续占用时段；确认必须同时具备店铺受理、本人任务确认、支付保障。
- 指名改派先征询，原始指名不变，同意后免指名费；不指名同店派发保留硬性语言条件。
- 服务完成与收款分开记录；演示支付同步模拟成功。真实 PSP 的异步确认、补偿与对账在 D 阶段实现。
- 安全事件写入 outbox 和审计；演示界面不会声称已联系真实紧急联系人。
