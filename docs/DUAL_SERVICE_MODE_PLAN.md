# 上门服务与到店服务：合并业务方案

日期：2026-10-26。

后续展示规则已按用户要求调整为“顾客主动选择”，取消浏览页顶部重复切换和默认上门，详见 [主动选择实现说明](SERVICE_MODE_CUSTOMER_CHOICE.md)。下文的通用业务与履约规则继续适用。

状态：本文件保留业务方案，合并 Codex 与 Claude 的观点。用户后续已授权按方案完善代码；首版实际实现、操作入口和验证边界见 [到店服务首版实现](DUAL_SERVICE_MODE_IMPLEMENTATION.md)。未确认的运营数值仍为建议，不能据此视为已批准的收费政策。

依据：用户提供的 Claude 方案、此前业务讨论、当前 V1.4 PRD 与共享合约、预约和履约实现。当前项目以纯上门业务为主，到店属于新增履约方式。

## 1. 产品定位与边界

一个平台提供两种预约服务：用户可以预约店铺安排技师上门，也可以在平台预约后前往实体门店。

继续沿用同一套顾客、商户、店铺、技师、订单、评价和售后体系。平台提供发现、预约和治理，店铺负责自己的服务、定价、受理和履约；本方案不新增平台自营技师业务。

必须分开的三个维度：

| 维度     | 选择           | 影响                                       |
| -------- | -------------- | ------------------------------------------ |
| 服务方式 | 上门、到店     | 地点、可售项目、价格、库存、政策、履约步骤 |
| 时间方式 | 尽快、指定时间 | 可约时间、响应时限和提醒                   |
| 人员安排 | 指名、店铺安排 | 人员承诺、指名费和改派                     |

现有 `bookingMode` 是即时/指定时间，不能拿它代表上门/到店。新增服务方式是独立概念；建议命名 `fulfillmentMode`，取值建议 `HOME_VISIT` / `IN_STORE`，最终名称留到实现阶段统一。

保留首页“选项目、选技师、选店铺”三个入口及现有视觉风格。三种入口最终进入同一预约链路，并全程携带当前服务方式。切换方式不能静默沿用另一种方式的价格、时段、地址或保留凭据。

## 2. 两份方案的共识与需要校正的分歧

| 议题                  | 合并后的建议                                                   | 原因                                                                               |
| --------------------- | -------------------------------------------------------------- | ---------------------------------------------------------------------------------- |
| 是否另建一套到店订单  | 共用订单主体，按服务方式分支                                   | 复用账号、权限、改派、评价、账务和售后                                             |
| 是否必须有真实门店    | 必须；实际接待地点与法定地址分别维护                           | 经营注册地址不等于可接待顾客的地点                                                 |
| 到店与上门价格        | 可分别配置；到店交通费固定为 0                                 | 两种服务的成本与优惠可以不同，不能一律用上门总价减交通费                           |
| 到店附加费            | 可以支持，但按方式单独配置并提前展示                           | 不能既允许配置又在总价中漏计；也不能默认继承上门深夜加价                           |
| 顾客迟到后的时长      | 默认仍以实际提供时长判定完成                                   | 不能因过了原预约结束时间就把不足时长的服务标为足时完成                             |
| 缩短时长、仍收原价    | 首版不采用为默认规则                                           | 若以后开放，需独立、明确的事先政策和本次确认，保留原购买时长与实际时长，走例外处理 |
| 取消与爽约            | 两种方式都有，分别定义触发证据和责任                           | 不能把取消费计算整体限制为上门，也不能仅凭未扫码认定爽约                           |
| 安全                  | 可分方式调整外勤签到，但两种方式均保留求助、私密投诉和平台通道 | 到店不代表没有安全问题，店长不能成为唯一求助接收方                                 |
| 现场付款              | 首版不新增，保留平台统一交易记录                               | 真实支付仍暂缓；现场付款将来可单独设计，不能说技术上必然无法收平台费或售后         |
| 72 小时无异议自动验收 | 属于需版本化的共同政策，先修复现有缺口                         | 不能机械复用当前有漏洞的实现；普通投诉应阻断，旧单不能被套上新规则                 |
| 首期即时到店          | 不做                                                           | 先完成预约、产能、核销和售后闭环，再增加排队与即时供给                             |

## 3. 供给与门店管理

### 3.1 店铺

店铺可以仅支持上门、仅支持到店或同时支持。第一期建议一个店铺对应一个实际接待门店；同一商户的其他门店使用其他店铺记录，连锁统一经营界面后续再做。

上门配置继续保留覆盖地区、接单时间、交通费和相关条件。到店配置新增实际地址、公开坐标、最近车站与路线说明、联系电话、门头及店内照片、到店营业时间、休息/临时停业、可用接待资源及清场时间。

门店信息通过平台审核后才能开放到店预约。地址等影响履约的重要信息变更，应重新核对或审核；不得修改已确认订单的接待地点。地点无法继续使用时联系顾客并走改约/取消，不能静默把用户导向另一家店。

现有资质和人员资格门禁继续生效。实体门店准入材料需要按实际服务类别另行明确，本方案不把“新增地址字段”视为完成场所资质审核。

### 3.2 项目与技师

项目分别设置可售方式、价格、时长、优惠、适用附加费和所需接待资源。可以共享项目介绍与分类，但上门和到店的可售报价应能独立维护。

技师由店铺配置可服务的方式与项目，并保留本人确认。技师不能借此自行修改价格；只接受酒店上门的限制仅作用于上门，不自动禁止其到店工作。所有模式仍需有效店铺绑定、身份核验、发布状态及项目资格。

展示与报价的交集为：店铺支持 ∩ 项目支持 ∩ 技师可服务 ∩ 人员可用 ∩ 地点/接待资源可用 ∩ 当前政策允许。

## 4. 价格、政策与订单快照

| 内容     | 上门                                   | 到店                                       |
| -------- | -------------------------------------- | ------------------------------------------ |
| 总价     | 上门项目价＋指名费＋交通费＋适用附加费 | 到店项目价＋指名费＋适用附加费             |
| 地区校验 | 顾客地址须在服务覆盖范围内             | 按所选实体门店，不限制顾客居住地           |
| 下单地点 | 本次顾客服务地址                       | 审核后的门店地点                           |
| 政策     | 上门取消、到达迟延、顾客失联等规则     | 到店取消、迟到、未到店、门店无法接待等规则 |

服务端计算总价。列表、筛选、排序、详情和结算都使用同一方式、项目、人员安排和时段下的价格；不同方式的价格不能混在一起作为同一筛选结果。

报价及订单需记录服务方式、经营主体与门店、地点快照、购买时长、价格明细、优惠、取消/迟到/爽约政策版本、完成验收政策版本及必要确认信息。已成交单不受后续改价和政策变动影响。

到店不收集无关的住宅地址或酒店房号。联系人属于订单联系信息，不应因去掉上门地址表单而丢失。

首版提交后不允许直接改服务方式或换店；需要明确取消原单并重新下单，并事先显示原单取消费用。修改时间也必须重新验证人员、资源和报价，不采用原地改时间绕过库存的方式。

## 5. 可约时间与产能

### 5.1 营业时间

分别维护上门接单时间和到店营业时间，支持休息、跨午夜与临时停业。到店默认需要在闭店前提供完整服务；例如 22:00 闭店，60 分钟项目的最晚正常开始时间为 21:00。清场时间还要纳入资源后续可用时间。

列表、报价、保留和最终下单使用同一规则。不能列表不显示某时段，但手工提交仍能成交；不能把上门目前“只约束开始时刻”的判断原样用于到店。

### 5.2 人员与接待资源

同一自然人的上门、到店、跨店时间共用日程。第一期以能独立接待一名顾客的床位或独占房间作为接待单元；同一物理位置不能既作为整间房又作为床位重复计算容量。

最小接待能力必须同时有可兑现的技师容量和相应资源。店铺安排也不能只凭空床接单；可以暂保留合格候选人员，再按现有规则派发与确认。

| 前后服务            | 排期考虑                             |
| ------------------- | ------------------------------------ |
| 同店到店 → 到店     | 实际服务占用、准备与清场             |
| 到店 → 上门         | 前一单结束、出发准备与交通           |
| 上门 → 到店         | 前一单结束、返回门店与准备           |
| 上门 → 上门         | 两个地点间的交通与准备               |
| 不同门店到店 → 到店 | 店间交通与准备，不能视作同店连续服务 |

第一期交通时间可使用统一、保守且可配置的估计，暂不依赖实时地图；具体默认分钟数待运营确认，不能假定任何距离都只需固定 30 分钟。

创建保留时一并占用人员和接待资源；转订单、改派、取消、超时、失败重试都应保持一致，不能只释放其中一项。并发抢同一床位只能有一笔成功。当前服务超时也要影响后续可接待能力，不能仅因计划结束就认定现场已空闲。

服务实际结束、必要清场完成后资源恢复可用；等待用户验收期间不应继续把床位占满 72 小时。

## 6. 两条履约流程与权限

### 6.1 上门

选择服务与地址 → 报价/保留 → 确认费用和政策 → 提交 → 店铺受理与派发 → 技师确认 → 出发 → 到达 → 开始 → 实际足时结束 → 用户验收/异议 → 评价与售后。

既有即时上门、指定时间预约、改派同意与安全流程继续保留。

### 6.2 到店

选择门店、项目、时间和人员安排 → 报价/保留人员与资源 → 核对地点、费用和政策 → 提交 → 店铺受理、人员确认 → 到店提醒 → 顾客到店 → 店铺核销签到 → 技师开始 → 实际足时结束 → 用户验收/异议 → 评价与售后。

到店新增清晰的“已到店/已核销”事实，建议使用独立 `CHECKED_IN` 状态或明确的核销轨迹；最终状态设计在实现前统一。不要伪造技师出发和到达顾客住所的记录来跳过现有门禁。

核销由有权限的店铺人员操作，仅限本店有效预约，核对预约凭证，记录操作人和服务端时间；防止猜码、重复、跨店以及取消后核销。顾客自报“我到了”可以作为提醒，不能单独替代店铺接待核实。

店铺核销不等于技师确认任务，不等于开始计时，更不等于顾客验收。前台角色可以先由有权限的店铺账号承担，不得因此获得代顾客验收或无限制查看信息的权限。

早到可在允许窗口内签到，首版正式服务仍不早于预约时间。签到本身不应提前占用技师正在服务另一单的事实状态。

## 7. 迟到、爽约、取消和安全

### 7.1 迟到

| 情况                         | 推荐处理                                                             |
| ---------------------------- | -------------------------------------------------------------------- |
| 顾客早到                     | 可核实到店，等待预约时间和资源就绪                                   |
| 顾客迟到且可继续提供完整时长 | 协商新的实际开始时间，先检查后续预约、资源和闭店时间                 |
| 顾客迟到且无法提供完整时长   | 联系改约或按已告知政策取消；不能自动缩短后判足时                     |
| 门店/技师原因未准时接待      | 记录服务方原因，提供按政策免费取消或顾客明确同意的改约，不算顾客爽约 |
| 顾客同意缩短服务             | 后续另设例外流程和金额确认；首版不作为默认正常完成路径               |

可将 15 分钟作为“建议讨论的迟到宽限”，但尚未确认；它不等于 15 分钟内必然可完整接待，也不等于超过后自动罚款。

### 7.2 未到店与取消

到店爽约以预约时间和事先告知的宽限为起点，由店铺记录联系尝试、等待与无法接待的实际情况后申报。系统先提醒和进入待核实，不能仅因未扫码就收费或处罚；已有到店、消息或服务记录应纳入核实，顾客保留申诉通道。

上门保留技师到达后的联系与等待规则。两种方式都有取消政策；店铺原因、明确无法履约、相关改派与免费取消条件继续适用。对“已签到但尚未开始”的顾客取消，需要明确阶段和费用，不能套用技师已经出发产生交通费的逻辑。

### 7.3 安全与完成验收

上门继续保留外勤安全签到和 SOS；到店可取消或调整外勤特有签到提醒，但仍保留紧急求助、私密投诉和平台安全通道。店长可参与处理，不作为唯一接收方；私密内容不能全部推送给被投诉店铺。

两种方式均按真实开始时间和购买时长核验服务，保留用户确认、异议、店铺复核及平台介入。平台判断工单完成与店铺实际执行、账务结果继续分别记录。

如果继续采用 72 小时无异议自动验收，必须明确告知并保存适用政策，计时基于真实结束，不得忽略普通售后工单或安全投诉；旧单按原规则处理。此前已复现的“普通投诉不阻断验收”和“旧单 24 小时自动验收”应在双模式交付前修复，不能视为可直接复用的已验收能力。

## 8. 四端体验、通知与经营

| 端           | 改动                                                                                                                                                                      |
| ------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 顾客 H5 / PC | 保留三入口与原配色；增加上门/到店选择；按方式展示供给、价格、时段和政策；到店结算显示门店与联系人，订单显示路线和核销凭证；切换语言、收藏、复购和分享链接保留有效服务方式 |
| 店铺         | 服务方式开关、真实门店审核、两套营业时间、分方式菜单/政策/优惠、资源日历、核销、迟到和未到店处理；上门与到店订单统一队列但清楚标识                                        |
| 技师         | 共用日程；上门保留出发/到达；到店显示工作门店、预约及签到情况，资源安排可见时再显示床位；本人开始/结束和异常操作不变                                                      |
| 平台         | 实体地点审核、按方式查单、容量和接待异常、到店未签到/迟延接待监控、工单和安全分流、分方式经营统计                                                                         |

到店订单必须有确认、变更、临近开始、取消、完成与工单更新等基础通知；服务地址与路线至少应在订单内可查看，不能把最基本的到店信息全部留到第二期。到店未签到是异常线索，并不自动证明顾客有错。

首版报表至少按服务方式标记订单、完成、取消、退款与投诉，统一金额口径；复杂经营看板可后续。房间号属于工作安排，不默认作为公开页面信息。

搜索中，上门地区代表覆盖范围，到店地区代表实体门店所在地；切换方式时应明确筛选含义。精确附近距离、车站筛选及专门 SEO 页面可后续；基础城市/地区与门店筛选首版应可用。位置权限拒绝时仍允许正常浏览，不伪造实时或精确距离。

| 前端预约、结算、订单、店铺/技师工作台                       | 多处文案和字段默认上门                              | 模式传递、门店/联系信息、核销、分方式操作与政策；保持三语及 H5/PC 一致 |
| `notifications.ts`、`governance.ts`、`reporting.ts`         | 以当前上门事件和订单口径为主                        | 到店提醒、接待异常、按方式统计与审计，保留隐私边界                     |

重要入口的当前行号：Store 144、Offering 168、Quote 231、quoteInput 570、bookingInput 592（共享合约）；buffered 309、availability 458、quote 563、createBooking 897、event 1523、noShowAction 1952（API engine）。实施时需重新核对行号，不能依赖本表作为固定接口定义。

## 10. 推荐分期与实施依赖

### 第一阶段：规则和数据准备

明确服务方式、价格/政策、到店营业时间、接待单元、核销与迟到流程。定义订单快照及兼容方式，修复已知验收问题。旧单明确按上门及原政策处理，未通过门店审核的存量店铺不自动开放到店。

### 第二阶段：预约到店闭环（首版交付范围）

交付门店审核与资源、可约和报价、人员+资源保留、下单/受理/改派、到店核销、真实时长服务、验收、取消/未到店、售后、基础通知、基础分方式统计，以及四端三语。保留现有上门功能和 UI 风格，真实支付接入继续暂缓。

### 第三阶段：搜索与经营增强

增加基于授权位置的真实门店距离、车站筛选、到店内容与落地页、经营对比、店内环境评价等。不得为了到店排名或宣传改写原有真实评价与数据。

### 第四阶段：复杂现场业务

即时到店和排队、加项/延时、复杂资源组合、连锁统一管理。加项需要追加报价、用户确认及相应资源校验；首版不提供原单直接加时或现场擅自追加费用的入口。

## 12. 后续验收清单

1. 三种入口、H5/PC、三语均可选择和保留服务方式；旧链接与旧单按上门兼容。
2. 仅上门店不能被预约到店；未审核或停业门店不能新接到店单；原有订单仍可处理善后。
3. 两种方式分别展示正确价格、优惠和政策；到店无交通费、无住宅/酒店地址要求，但有联系人。
4. 相同技师的上门、到店和跨店订单互斥；转换缓冲、请假、休息、实际服务超时都生效。
5. 两名技师争用一个接待单元时只有一单可提交；取消、过期、提交失败及改派不泄漏库存，也不重复释放。
6. 到店项目能在营业时间内完整提供；跨午夜、临时停业、关闭日期边界和最后可约时段一致。
7. 非指名单也有可兑现人员容量；改派人员合格且资源可用；指定人员变化需要顾客同意。
8. 核销仅限本店有效单，重复、猜码、跨店和取消后核销均被阻止；扫码不等于开始/完成。
9. 顾客早到、迟到、未到，店铺未开门、技师迟到与前单超时分别按实际责任处理。
10. 服务不足时长不得进入正常足时完成；未扫码但存在到店/服务证据不得直接认定爽约。
11. 普通售后及安全投诉阻断不当自动验收，旧单不被新政策自动完成；新单按已告知版本执行。
12. 到店同样支持投诉、私密求助、平台介入、退款善后和基础通知；权限与敏感信息不因增加核销而扩散。
13. 资源实际释放与待验收分离；验收等待不能长期锁住已清场床位。
14. 店铺、平台统计可以区分两种方式，金额与取消退款口径一致；统计不把未验收保障额当作收入。

以上是方案阶段整理的验收要求；后续已授权实施，实际覆盖与结果见 [首版实现记录](DUAL_SERVICE_MODE_IMPLEMENTATION.md)，不能仅凭本清单认定全部验收通过。
