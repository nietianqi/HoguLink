# PC 用户端改造方案：业务、流程、信息架构与视觉

日期：2026-10-29（日本时间）

代码基线：`2cee8e5`

状态：已合并双方评审并实施首轮改造，详见第 13 节。业务接口保持兼容；测试数据仅在隔离环境生成。

## 1. 结论与边界

现有业务主干可以保留：店铺作为服务合同主体，顾客通过项目、技师、店铺三个入口预约，上门与到店分别报价、匹配产能和履约，完成后由顾客验收，并有取消、改派、评价和售后。

PC 用户端的主要问题是**业务事实与页面表达不完全一致，选购信息与管理工具混排，核心操作被大标题、整份菜单和重复模块推到后面**。首先纠正这些问题，再调整布局，最后收敛视觉。

本方案不恢复已撤回的 [旧用户端简化方案](UI_SIMPLIFICATION_PLAN.md)。保留当前绿色主题、现有首页图片、项目／技师／店铺三个选择入口、商户与技师入驻入口及现有真实内容。PC 不以简单放大 H5 或更换全站主题完成改造。

业务依据按当前代码、[四端业务逻辑](BUSINESS_LOGIC.md)、[服务方式主动选择](SERVICE_MODE_CUSTOMER_CHOICE.md)、[双服务方式实现](DUAL_SERVICE_MODE_IMPLEMENTATION.md)核对。旧讨论中的“默认上门”“到店迟到就缩短时长”等说法不作为实施依据。

真实支付继续暂缓；已有模拟保障、价格、幂等和验收门禁不删改。本方案也不增加技师抢单、平台代发工资、钱包、充值或未接通的在线客服承诺。

## 3. 优先级 0：业务逻辑与职责

### 3.1 平台模式与角色

| 角色 | 承担职责                                                                 | 不应转嫁给顾客或其他角色的工作                     |
| ---- | ------------------------------------------------------------------------ | -------------------------------------------------- |
| 顾客 | 选择项目、服务方式、人员偏好、时间和地点；同意改派；验收；评价；申请售后 | 不理解派单、员工任务、内部工单分组也应能完成预约   |
| 店铺 | 定价、受理、安排人员、处理履约与退款、承担服务合同                       | 自动受理不能替代技师确认；不能代顾客同意改派或验收 |
| 技师 | 确认本人任务，按方式履约，提交服务与异常事实                             | 不向顾客独立售卖、决定退款或代顾客确认完成         |
| 平台 | 审核、交易协调、投诉、安全与权限治理                                     | 不因审核标识、年费或推荐位承诺服务效果、伪造评分   |

顾客页面只需清楚传达：**向哪家店预约、谁提供服务、在哪里服务、何时开始、多少钱、下一步由谁处理。** 后台的全部内部状态不应原样成为顾客页面的模块。

### 3.2 四个维度必须分开

| 维度     | 可选项             | 决定什么                                           |
| -------- | ------------------ | -------------------------------------------------- |
| 浏览入口 | 项目／技师／店铺   | 从什么信息开始选择，不生成三套订单系统             |
| 服务方式 | 上门／到店         | 地点、菜单价格、服务资格、产能、履约步骤           |
| 人员偏好 | 指定技师／店铺安排 | 指名费、人员承诺、改派需否征得同意                 |
| 时间方式 | 指定时间／即时     | 真实可约性、受理范围、回应时限；到店首期仅指定时间 |

“选店铺”不等于“到店”，“选技师”也不等于“上门”。“即时”不等于“技师在线”，也不能由浏览卡片直接承诺立即到达。

三条路径最终汇入同一预约选择：

- 项目入口：保留当前店铺的真实项目，顾客可指定技师或由该店安排。
- 技师入口：携带该技师与所属店铺，顾客确认服务方式后选择可承接的项目和时间。
- 店铺入口：默认人员偏好为店铺安排；顾客主动选人后才产生相应指名费用。

同名项目不能跨店合成一个可成交项目。可以做分类和比较，但报价始终落到真实店铺、真实 SKU、真实服务方式与时长。

### 3.3 服务方式的选择时点

1. 浏览时同时展示合格供给，价格旁明确“上门／到店”及对应时长；筛选只是浏览意向。
2. 详情预约区或独立预约页，先由顾客主动选择服务方式，再查询对应项目、费用和时段。
3. 只有一种方式也明确告知并让顾客确认；不恢复自动默认。
4. 同一笔预约已确认方式后，跳页和语言切换保留结果，不要求重复选择。
5. 更换方式重新校验项目、技师、价格、语言与资源，旧时间失效；只保留仍兼容的同源项目。
6. 提交后方式与地点快照不可改；切换方式需遵守原单取消流程后重新预约。

`modeConfirmed` 只是界面上下文；金额、库存、权限与合法方式仍由服务端校验。旧链接只带 `fulfillmentMode` 时仍需主动确认。

### 3.4 价格与承诺口径

列表显示“某服务方式 · 某时长 · 起价”，预约条件未完整时显示估算，最终确认只使用服务端报价。

最终金额保持：生效服务价 + 指名费 + 上门交通费 + 适用时段附加费。到店交通费为 0；店铺安排指名费为 0。地区或时间尚未选定时，不把基础估算包装成固定全包总价。

- 上门与到店金额分别展示，不能用到店最低价吸引上门预约。
- 技师价格与店铺安排价格标明不同人员偏好；“已含指名费”与“+指名费”不可在相邻区域造成重复收费的视觉暗示。
- 有真实有效比较价才划线，优惠结束后重新报价；不创造销量、评分、距离或可约时间。
- 报价及取消政策冻结在订单里；公开价格或菜单后续改变不能重写历史订单。
- 取消前请求实际费用预览，确认时重新检查版本与费率档位；不在前端猜收费。
- 模拟授权、已扣款、退款申请、退款执行是不同事实。支付暂缓不等于删除这些边界。

### 3.5 状态流转与顾客动作

保留后端状态机，通过顾客视图解释，不为视觉简化合并存储状态。

```mermaid
flowchart LR
  A[选择项目、技师或店铺] --> B[主动确认上门或到店]
  B --> C[选择人员偏好与有效时段]
  C --> D[服务端报价并暂时保留]
  D --> E[确认地点、费用、政策并提交申请]
  E --> F[店铺受理与技师确认]
  F --> G{服务方式}
  G -->|上门| H[出发、到达、开始]
  G -->|到店| I[前往门店、核销、开始]
  H --> J[足时结束]
  I --> J
  J --> K[顾客验收或提出问题]
  K --> L[评价、售后、再次预约]
```

| 当前事实                | 顾客应看到的说明                         | 首要动作或反馈                         |
| ----------------------- | ---------------------------------------- | -------------------------------------- |
| `CHECKOUT_HOLD`         | 时段暂时保留，尚未提交；剩余多久         | 继续填写／主动修改并释放原保留         |
| `REQUESTED`             | 申请已提交，店铺受理中                   | 告知预计回应截止，保留联系和取消入口   |
| `ACCEPTED` 且技师未确认 | 店铺已受理，正在确认技师                 | 明确等待，不显示预约已经确认           |
| 改派待同意              | 原人员变化、候选人员、费用变化、处理截止 | 查看并同意／拒绝；不能默认同意         |
| `CONFIRMED` 上门        | 已确认，技师将按约上门                   | 查看地址与时间，联系店铺               |
| `CONFIRMED` 到店        | 已确认，请按约到店                       | 门店地址、路线与核销码；签到后等待服务 |
| `EN_ROUTE`／`ARRIVED`   | 技师已出发／已到达                       | 查看进度、联系、按实际规则处理延迟     |
| `IN_SERVICE`            | 服务中，实际开始与预计可完成时间         | 保留联系和报告问题，未足时不能提前验收 |
| `AWAITING_COMPLETION`   | 服务已结束，请核对实际记录与金额         | 确认完成／提出异议，显示适用截止       |
| `COMPLETED`             | 已完成；评价与售后仍可进入               | 写评价或再次预约                       |
| 取消／拒绝／超时        | 预约未继续履约，解释实际原因与费用结果   | 重新选择，查看费用和售后               |

平台安全、服务异常、支付保障失效、改派同意、验收及退款分别保留独立轨迹。紧急问题入口持续可用；“每个状态一个主操作”不意味着隐藏安全、异议和取消权利。

顾客端提示优先级：紧急安全 → 当前阻断事项 → 改派／验收等待决定事项 → 正常进度 → 次要历史信息。不能只按一个 `status` 字符串决定所有按钮。

自动验收继续以服务端返回的资格为准：足时、适用的 72 小时政策、无未解决异议／工单／安全异常、有效保障等条件必须满足。店铺不可替顾客确认，工单关闭也不表示退款已到账。

### 3.6 异常闭环

| 场景                             | 必须保留的反馈和恢复方法                                                       |
| -------------------------------- | ------------------------------------------------------------------------------ |
| 没有匹配项目／人员／门店         | 解释具体不匹配条件，允许清除单项筛选；空结果不伪装成系统错误                   |
| 查询失败                         | 保留选择并提供重试；与“没有时段”区分                                           |
| 时段被占、资源不足               | 说明原时段不可用，保留兼容条件并重新选时；不偷偷替换                           |
| 未提交报价过期或价格政策变更     | 显示需要重新核对；禁止沿用旧总价提交                                           |
| 保留超时                         | 说明未提交成功，可重新查询；已提交的保留必须恢复原单，不能再建一单             |
| 登录过期／邮箱未验证             | 解释下一步，完成后返回原选择；不能把旧报价恢复成仍然有效                       |
| 重复点击／网络丢失响应           | 按原幂等键查询提交结果，先恢复已创建订单，再允许重试                           |
| 技师拒绝或需要换人               | 明确由店铺安排；指定人员改派须顾客同意，不能跨店改原交易                       |
| 顾客或技师迟到、无法服务         | 分清责任、原承诺与当前可否足时履约，使用现有政策；不增加默认缩时或自动收费规则 |
| 到店未核销／顾客未到             | 核销不等于开始；未核销不等于爽约；按联系、等待与核实流程处理                   |
| 资料下架、店铺暂停或公开目录失败 | 本人的订单、冻结项目、地点和售后仍可访问，不依赖当前公开供给是否存在           |
| 退款进行中／售后工单未解决       | 分别显示处理人、下一步、退款实际状态，不用“已解决”覆盖全部事实                 |

## 4. 优先级 1：让用户更容易完成业务

### 4.1 浏览到预约

- 首页选择入口提早出现。搜索按钮和落地结果一致：选择“技师”就到技师结果，不滚到项目面板再让顾客自己找。
- 三个目录共用筛选含义、费用展示和选择上下文；页面仍各有重点，不强制改 URL 或合并成一张巨型表。
- 从项目选人弹层保留“由店铺安排”方案，不强迫用户必须指名。
- 已选项目显示紧凑摘要和“更换项目”，不默认重复展开全部菜单。主动更换时才展开候选。
- 技师选择后保留服务方式、合法项目与语言等兼容条件；新条件需要重查时明确说明。
- 技师／店铺详情的预约侧栏与独立预约页复用同一选择状态与规则，而非两套不一致表单。

### 4.2 预约与结算

维持三段心智：**选择服务与时间 → 确认地点和费用 → 提交申请并等待确认**。它描述任务，不要求人为增加三个全新的页面。

PC 左边完成当前步骤，右边固定显示本次摘要：店铺、技师或店铺安排、服务方式、项目时长、JST 时间、价格明细、当前主操作。已完成项可编辑，编辑前说明受影响内容；未完成项旁说明为什么不能继续。

上门填写常用地址或酒店信息；到店只显示已审核门店与联系人，不出现住宅、酒店房号或上门地区输入。沿用地址草稿、酒店许可、地区与酒店限制校验。

把长规则改为“关键摘要 + 完整规则”两层，提交前仍可读到金额、经营主体和政策。核对弹层只展示最终关键事实，不再重复填表。按钮文案明确是“提交预约申请”，成功后明确“受理中”，不宣称服务已安排。

时段保留倒计时靠近本次摘要；在临近到期和到期时告知恢复方法。不连续打断、不靠重载延长。保留、登录回跳、最终报价、提交恢复等现有保护不因减少点击而删除。

### 4.3 订单、消息与售后

订单首屏回答六件事：状态是什么、下一步谁处理、何时服务、谁来服务、在哪里、如何联系。

到店突出门店／路线／核销，上门突出服务地址／人员／进度。正常状态不展开整套退款说明；有退款、异议或安全事项时主动显示对应模块。

一个订单内整合“联系店铺”和“查看处理结果”，消息中心保留跨订单收件功能。进入售后自动携带订单和问题类型，少填一次信息；只有需要平台处理的隐私或安全内容按既有权限规则隔离。

订单进度、消息和工单仍是独立事实，统一的是顾客入口与解释。保留所有历史工单、退款记录和冻结政策，不通过“简洁”删除访问能力。

## 5. 优先级 2：PC 信息架构与布局

### 5.1 导航分工

建议 PC 主导航采用“首页｜选项目｜选技师｜选店铺｜发现”，直接对应三个选购入口。消息、我的预约与个人账户属于右侧工具区，在较窄 PC 宽度把次级项收入账户菜单；不挤压主业务导航。该导航为建议结构，实施先核对 1280px 与三语长度。

不新增第二套业务路由：项目沿用 `/services`，技师沿用 `/therapists`，店铺先沿用 `/discover?tab=shops`，店铺详情沿用 `/shops/{slug}`。可共享顶部选购导航，但不要求删除旧入口或重定向历史链接。发现默认以内容、指南和真实店铺动态为主，避免顾客必须猜“店铺藏在哪个内容标签”。

H5 保留现有底部五入口。PC 与 H5 共享业务、数据与价格口径，导航布局适应设备，不强求一模一样。

### 5.2 页面职责与布局

| 页面       | 核心问题                               | 建议布局与主操作                                                                                  |
| ---------- | -------------------------------------- | ------------------------------------------------------------------------------------------------- |

| 项目列表   | 这是什么、多久、哪家店、对应方式多少钱 | 紧凑标题＋筛选条；卡片按店铺真实项目展示；主操作“选择人员与时间”                                  |
| 技师列表   | 谁适合我、能否服务、何时可约           | 2–3 列可比较卡片，统一照片、姓名、店铺、语言、方式价与最早时间；主操作“查看时段”                  |
| 店铺列表   | 哪家店可信、能提供什么、如何预约       | 品牌与能力卡；清楚区分上门品牌和已审核实体门店；主操作“进店查看”                                  |

### 5.3 首页具体处理

业务区块与当前三个页签保留。PC 优化顺序是：

1. 顶部保留 Logo、城市／地区上下文、语言和主导航。
2. 现有绿色横幅与照片继续使用，减少上下高度与重复宣传句。
3. 三个业务入口紧接横幅或与轻筛选组成一个完整选购区，在 1280×720、1440×900 首屏可看到核心入口。
4. 选中维度显示相应精选，另一维度一击可切换；条件变化或回退时保留所选维度。
5. 活动存在时显示现有限时优惠，不为填版编造；完整筛选与完整目录交给对应结果页。
6. 保障、商户与技师入驻保留在业务内容之后；个人预约、收藏、记录通过工具区和账户侧栏访问。

不在首页再增加一组大“上门／到店”切换。浏览卡片标清能力与价格，预约区保留主动选择。

### 5.4 详情页与订单的首屏

技师详情第一屏须能找到姓名、所属店铺、主要语言、服务能力和预约入口。照片、视频用于辅助判断，不能把身份信息全部挤到下屏。无视频不留空位，不自动播放或出声。

订单详情第一屏优先展示状态与实际下一步，包含联系人、服务方式、JST 时间和地点摘要。完整六阶段进度条可以保留为次级解释，但不应先占满首屏，再让顾客滚动寻找自己的预约内容。

## 7. 可访问性与人性化检查

本轮看到跳至正文、字段标签、文字状态和部分选中语义，是可保留的基础。但截图不足以证明可访问性合格。

实施必须检查：键盘完整完成筛选、选择和提交；弹层打开后的焦点、关闭后的返回焦点与 Escape；日期／时段选择可感知；错误关联字段且指向恢复动作；禁用按钮同时解释原因；页面缩放到 200% 仍可用；尊重减少动画设置。

普通文字以至少 4.5:1 对比度作为验收目标，不能只根据品牌色十六进制判断。倒计时不逐秒打断读屏，临近结束和失效通过适当状态提示。固定摘要不能挡住字段、错误和页面底部。定位为自愿，拒绝定位仍能手动选地区。

## 10. 应保留与暂不增加的内容

应保留：三入口、照片视频和审核、店铺品牌内容、真实评价与店铺回复、两种服务方式、人员偏好、即时与指定时间、费用冻结、取消预览、改派同意、足时验收、消息、所有售后记录及商户／技师入驻。

暂不增加：跨店购物车、为比较而强制选 3 人、首页多级营销楼层、未接通的在线客服、虚构优惠券／余额、播放量／人气、承诺实时定位或到达时间、真实支付渠道。先减少当前核心业务的理解成本。

## 11. 商业产品的验收目标

- 第一次进入 PC 首页，能立即指出项目、技师和店铺入口；主流程不依赖阅读宣传段落。
- 任意价格可以说清对应的店铺、方式、时长、人员偏好和是否最终报价。
- 同一笔预约不重复填写兼容信息，不因语言切换丢失选择；变更导致失效时明确说明。
- 服务方式必须由顾客自主确认；所有后续页面一致，不能在到店单显示等技师出发。
- 顾客能分清申请已提交、店铺受理、预约已确认、服务结束和验收完成。
- 订单首屏可判断下一步、责任人、时间、地点与联系方法；异常有解释和恢复路径。
- 在目标 PC 尺寸首屏出现主入口／当前任务，避免被标题、重复工具或空统计占满。
- H5 核心流程与三语不回归；没有为了“更高级”牺牲可读性、规则披露或操作能力。

以上是持续验收目标，不代表所有指标均已完成测量。完成后可再观察选购到选时、选时到提交、提交到确认的漏斗，以及输入错误与恢复成功率；不在未建立基线前承诺转化提升比例。

- 采纳共同选择上下文、已选项目摘要、先选地区、详情直接选时并保留、顾客状态卡、减少重复导航、PC 双栏与绿色主题统一。
- **服务方式不自动默认**：Claude 建议单一方式自动选中，但用户之前明确要求顾客自主确认。继续遵守该要求；同一次选择通过 URL 保留，不在下一页重复询问。
- **同名项目不跨店合成交易**：保留真实店铺、SKU 与方式价格，列表可比较，实际成交不混合经营主体。
- **不承诺所有待确认取消免费**：沿用服务端取消费用预览与冻结政策，不用状态名称推断费用。
- **保留现有能力**：导出进入“更多工具”；日期、预算、受理方式和视图等高级筛选迁至专门的技师结果页，而非删除。
- 保留日元明确标识和真实支付边界；不按未经测量的“5 次点击”“最多 2 屏”宣称完成，不为视觉指标删掉必要业务信息。

### 已实施

1. 顾客订单有独立的下一步映射，区分店铺受理、技师确认、重新安排、改派、支付保障、两种履约、验收与关闭。到店页显示门店地区、路线与核销，移除通用上门指引。
2. 店铺“自动确认”改为自动受理，明确技师确认后生效；原有后台与接口规则不变。
3. 首页搜索直接进入技师结果。移除首页隐藏的整套目录与逐技师时段查询；原高级筛选、价格／最早排序、卡片／列表视图在 `/therapists?filters=advanced` 延续，旧首页高级条件链接转入对应结果。
4. 上门预约不再把未知地区默认成第一个地区。未选择时不查询时段、不显示完整预估总价，也不能创建报价保留；到店地区来自已审核门店。
5. 已选菜单摘要化，可主动更换。地区、语言、人员偏好或服务方式改变时清除不兼容的时间；同一项目重复点击不再清空时间。
6. 技师和店铺详情复用 `/book` 的报价与保留逻辑，登录回到原详情的已选上下文；独立 `/book` 与旧链接继续可用。
7. 结算页表单、摘要及手机操作栏共用下一步文案，仍保留原生字段校验、政策同意和最终核对。默认地址为住宅，但仅酒店技师强制酒店；旧地址草稿、房号及酒店许可的隐私规则保留。
8. 我的预约移除正文重复快捷导航和经营统计，PC 使用服务内容优先的订单卡片。未扣款且无退款记录时隐藏空金额卡，所有已存在的退款与工单仍可访问。
9. PC 导航明确三个选择维度；首页横幅收紧，详情身份前置、结算摘要顶部对齐、项目使用现有示意图片。H5 首页和底部主导航保留，布局调整主要限定在 1101px 及以上。
10. 预约及结算中的默认演示头像与目录使用同一映射；自有上传图片与非演示资料不替换。空评价在 PC 详情以真实汇总文字表达，不填假评分。
11. 高级筛选的卡片价格、菜单和排序使用当前方式、时长及预算下的候选项目，避免“筛选内有低价，卡片却推荐超预算项目”。到店地区标签及零交通费口径同步修正。

### 实现与验证边界

前端采用已有共享规则和新增的顾客状态视图，不更改服务端状态、价格、资源、版本或权限接口。取消费用预览原已实现，本轮保留并回归，没有另建一套取消计算。

历史 CSS 未一次性清空；在既有消费者样式层内限定 PC 作用域，未新增全站主题或 `!important`。新开页面仍可后续逐项清理历史规则。优惠券、真实支付、推送及正式渠道送达未扩展。
