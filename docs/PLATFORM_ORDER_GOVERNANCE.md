# 平台订单监控、异常预警与售后复核

更新：2026-10-18，第十九轮。覆盖日文、英文、简体中文的 PC 与手机页面；延续深绿、暖白、细边框与克制留白。当前是本地演示。

## 同行观察与产品边界

参考 [くらしのマーケット官方纠纷与补偿说明](https://faq.curama.jp/docs/user/trouble-and-compensation/)中的店铺沟通、未响应跟进与退款责任，以及 [HOGUGU 官方帮助](https://info.hogugu.com/guide.html)的到达延迟联络、订单变更入口。くらしのマーケット明确不代替双方判断争议事实、进行仲裁或执行退款；本项目没有声称同行具有这些能力。

HoguLink 的平台调查与处理结论依据本项目 V1.4 的 A06、21.4、37.2 等条款实现，作为可追溯的协调方案，不宣称具有法律仲裁裁决效力。原店铺执行常规退款，平台保留调查、跟进、治理与审计职责。没有套用同行费率、赔偿承诺或品牌视觉。

## 已完成的业务

### 订单监控与预警

入口：`/{locale}/admin?tab=orders`。监控面板提供待处理、高优先级、本人关注、跟进超时、已恢复、关键词搜索与分页。条件来自真实订单、工单、安全和退款记录，不通过装饰性状态推断完成。

| 预警           | 当前演示规则                                                           |
| -------------- | ---------------------------------------------------------------------- |
| 接单响应       | 店铺受理或技师回应期限剩余 5 分钟以内                                  |
| 技师安排受阻   | 拒绝、撤回任务，或确认订单仍需安排人员                                 |
| 改派同意       | 原改派期限剩余 5 分钟以内，不延长原期限                                |
| 到达延迟       | 即时单使用冻结的原到达承诺与原宽限；预约单超过预约开始 15 分钟仍未到达 |
| 服务结束超时   | 实际开始时间加原服务时长，再超过 30 分钟                               |
| 爽约待审       | 技师已申报，尚待原有流程核验                                           |
| 支付待核验     | 实际支付状态为失败或退款处理中                                         |
| 安全未解除     | 尚未解决的安全事件，仅有安全权限者可见                                 |
| 售后响应超时   | 未结束工单超过原回复期限                                               |
| 工单跟进到期   | 内部安排的跟进时间到期                                                 |
| 退款处理超时   | 退款申请建立满 24 小时仍待决定                                         |
| 处理结果待复核 | 退款执行与平台方案不符、余额被其他退款改变，或顾客重新申诉             |

这些阈值是本项目演示规则，不是同行服务承诺，也不会自动更改取消费或赔偿政策。

预警使用稳定标识、版本和发生轮次。关注会认领给当前员工，可选未来 24 小时内的跟进时间，并记录内部说明；释放关注会回到待关注。另一员工的关注需分派权限才能接手。关注与释放都不能手动把异常标成已恢复；只有真实业务条件消失才恢复。观察到恢复后再次出现，会开启新轮次并清除旧负责人。

每次操作重新核验当前订单或工单版本。超时的跟进仍留在待处理队列。普通只读岗位可看权限内预警状态，不返回内部跟进说明或负责人标识；私密工单按业务组隔离，安全事件按安全权限隔离。

### 售后调查、处理结论与核验

1. 顾客从原订单申请退款或发起售后；店铺先受理，争议可升级平台。
2. 店铺从工单的「核实技师履约事实」进入准确原订单，通过既有店内协作收集对应技师事实。技师只向原店铺提供事实，不接收顾客私密工单、退款余额或平台内部备注。
3. 平台引用原始申诉和本工单的店铺陈述，填写核实事实、结论依据及后续安排。店铺完全未陈述时，建立满 24 小时后才能明确记录未响应例外；已有店铺陈述不能使用该例外。
4. 「建议退款 / 建议不退款」必须绑定待处理的顾客退款申请，金额不超过申请金额与实际剩余余额。发布本身不改变订单、不执行退款。
5. 原店铺独立处理退款。实际批准金额与建议金额一致，或不退款方案对应实际拒绝，才能进入可结案；少退、拒绝退款建议、撤回申请或待执行时余额被其他退款改变，都会要求复核。
6. 「跟进整改或说明」必须由原店铺提交执行回执。回执不移动资金；仍有待处理退款时也不能结案。新修订不会沿用上一版回执。
7. 平台核验后记录结案。顾客可查看事实、理由、实际退款、执行回执和历次结论，并可按原有流程重新申诉。重新申诉会使旧的核验失效；再次发布方案必须引用顾客最新的重新申诉陈述。

发布同时核对工单、结论、订单、退款申请四个版本。页面打开表单时固定这些版本，防止轮询悄悄替换确认依据。重复提交使用与内容绑定的重试键，保留不可覆盖的结论历史，最多 50 版。陈述校验失败保留表单与草稿；状态已改变时要求重新核对。

非分派岗位须先认领工单，且只能处理授权业务组。普通工单结案入口同样检查退款与方案执行，不能绕过核验。平台资金接口仍不能代原店铺退款。

### 四端联动与隐私

平台关注履约异常后，原店铺和当前合法获派技师的订单协作显示必要的关注提示；顾客仅收到与本人到达延迟相关的提示。所有提示在返回前再次检查实际订单条件，技师记录实际到达后，三端提示立即恢复，无需等待平台下次刷新。

提示不包含内部说明、负责人、跟进时间或私密安全/售后工单。店内技师原始说明不会自动变成平台证据，由店铺核实后补充共享陈述。平台队列不返回顾客地址、手机号、健康资料或支付路由。

订单监控、订单协作与售后在页面可见时每 15 秒刷新，窗口重新聚焦时核对。顾客站内消息依据工单版本提示更新。通知队列仅保存引用，不放入调查、投诉或内部备注正文。

## 接口

以下路径均以 `/v1/` 开头。

| 接口                                               | 权限与主要字段                                                                                                                                                              |
| -------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `GET admin/order-monitor`                          | `orders.read`；返回权限内预警、服务端时间及规则摘要                                                                                                                         |
| `POST admin/order-alerts/:id/follow-up`            | `orders.read`、`cases.write`；`version, action: WATCH/RELEASE, followUpAt, note`；安全警报另需安全权限，版本竞争返回 409                                                    |
| `GET support-tickets/:id/decision`                 | 顾客本人、原店铺、可见业务组的平台员工；技师禁止读取；返回结论历史、当前核验状态及最小执行回执                                                                              |
| `POST support-tickets/:id/decision`                | 当前可写、可见的平台员工；`ticketVersion, version, bookingVersion, refundVersion, outcome, amount, summary, reason, evidenceIds, merchantUnreachable`；需 `Idempotency-Key` |
| `POST support-tickets/:id/decision/acknowledgment` | 原店铺；`version, ticketVersion, text`；需 `Idempotency-Key`，只能确认尚未回执的当前整改方案                                                                                |
| `GET bookings/:id/coordination`                    | 新增最小 `platformAttention: {kind, firstSeenAt}[]`；限定当前合法关系与提示白名单，重新核对实际条件                                                                         |

`support-tickets/:id` 同时返回可核验的 `decision` 摘要；技师视图不返回财务结论。`RESOLVE/CLOSE` 共用执行核验门禁，顾客 `REOPEN` 保留原历史并要求重新审查。

记录保存在既有事务存储的 `orderAlerts`、`orderAlertHistory`、`caseDecisions`、`decisionReceipts`、`decisionIdempotency` 中，无需修改通用 records 表结构。`TicketMessage.ticketVersion` 是兼容旧数据的可选字段，用于同一时点多次申诉的顺序确认。审计和本地通知仅存必要引用。

## 后续生产接入

真实身份、PSP 异步退款与对账、邮件/LINE 可靠投递、附件证据保全、真实设备及生产并发验收仍待接入。本轮整改回执是店铺陈述与平台记录，并不等同于外部事实自动取证。

监控目前由页面轮询时对照实际记录，不是持续运行的后台告警服务；轮次表示平台观察到的恢复和再发生。上线前需独立调度、正式营业日历/SLA、投递重试与升级机制、规则配置审核，以及容量与留存策略。既有演示允许提前推进未来任务步骤，不代表已实现真实履约时点验证。
