# 四端业务逻辑评审

日期：2026-10-26。代码基线：`ff41a33`，分支 `main`。

本次从产品经理视角核对顾客、店铺、技师和平台的职责、状态、费用、异常负责人及超时善后。真实支付接入按要求暂缓，仅验证既有模拟保障和账务规则。未修改业务代码，也未推送。

证据来自当前源码、当日运行的自动化回归，以及一次性内存数据库中的专项复现。浏览器连接返回 `privileged native pipe bridge is not available; browser-client is not trusted`，因此本报告**不是页面截图体验审计**；不声称完成四端页面逐项点击、真机、读屏或外部通知送达验收，也没有使用历史截图代替本轮证据。

## 一、结论

主交易的职责划分和大部分状态保护成立：顾客向店铺预约，店铺受理与技师确认分开；指定人员改派需顾客同意；服务结束后由顾客验收；退款由原店处理，平台调查结论与实际执行分开。

但当前仍有 **1 类 P1、4 类 P2，共 7 个具体问题**。最优先是安全事件的跨端漏报，其次是待派单超时提醒。正常交易回归通过，不能证明这些异常场景已经覆盖。

| 端         | 已验证的主干能力                                                   | 当前问题                                                              |
| ---------- | ------------------------------------------------------------------ | --------------------------------------------------------------------- |
| 顾客 H5/PC | 三入口进入同一预约、报价保留、原单恢复、改派同意、验收、原订单售后 | 价格展示/筛选三处不一致；可约时段与下单时间口径不统一                 |
| 店铺       | 人工/自动/SOLO 受理、派发、改派、拒绝、取消、退款及工单执行        | 待派单超时未完整接入平台预警；营业时间尚无统一供给判断                |
| 技师       | 本人任务确认、合法任务访问、出发/到达/足时履约、事实协作、安全报告 | 即时单按承诺到达后可能仍需等待才能开始；SOS 到订单监控链路断开        |
| 平台       | 员工权限、工单分派、调查、原店执行核验、重新申诉、账务查询         | 综合订单监控遗漏真实 SOS 和部分待派单；专项测试存在错误数据源掩盖问题 |

## 二、需要优先处理的问题

### 1. P1：真实 SOS 不进入综合订单监控的安全预警

**涉及端：技师 → 店铺/平台。**

技师安全报告和安全签到升级写入 `safety`。安全事件列表也读取 `safety`，但订单监控读取 `safetyEvents`，没有连接同一数据源。

专项复现通过正常任务、技师确认及 `engine.safety(..., 'SOS', ...)` 发出事件，结果为：

| 观察项                               | 实际结果 |
| ------------------------------------ | -------- |
| 安全事件列表中的该订单 SOS           | 1 条     |
| 综合订单监控中的该订单 `SAFETY_OPEN` | 0 条     |

这不代表 SOS 完全丢失：独立安全列表能够看到；问题是依赖综合订单监控值守的员工可能收不到对应预警。

定位：`hogulink-api/src/governance.ts:497`、`hogulink-api/src/engine.ts:2230`、`hogulink-api/src/fulfillment.ts:160`。

已有 `governance.test.ts` 的相关测试直接往 `safetyEvents` 写假事件，因而验证了监控分支，却没有验证真实技师上报链路。

建议：统一安全事件数据源；让回归从技师实际发出 SOS/未签到升级开始，覆盖平台出现预警、合法员工认领、解除事件、监控恢复。外部通知是否真正到达及是否有人值守仍要另行验收。

### 2. P2：自动受理的不指名即时单，待派人超时前没有平台预警

**涉及端：顾客 → 店铺 → 技师 → 平台。**

此类订单会进入 `ACCEPTED + NOT_SENT + assignedStaffId=null`，需要店铺及时派人。当前 `RESPONSE_DUE` 只检查待店铺受理或已发送技师任务，`ASSIGNMENT_BLOCKED` 又没有包含这类已受理未派发订单。

专项复现：创建不指名即时单，推进到响应截止前 1 分钟，店铺仍未派发。平台两类预警均为 false，订单预警数为 0；再推进到截止后，订单直接变为 `EXPIRED`。

店铺自身待办可以看到待安排订单，本项不是整个派单入口失效，而是平台异常监督在最需要提醒时缺了一段。

定位：`hogulink-api/src/governance.ts:38–48`。

建议：统一“还需谁在截止前动作”的判断。待受理、待派人、待技师回应、待顾客同意分别显示明确负责人和原截止时间，按紧迫程度进入监控；提醒本身不能代店铺派单或代顾客同意。

### 3. P2：即时单的到达承诺与允许开始时间没有对齐

**涉及端：顾客、技师、店铺。**

即时可约接口返回一个预计开始时刻，技师确认时又可选择 30–60 分钟到达。实际开始接口对即时单也一律要求到报价的 `startAt`。

专项复现：09:00 下即时单，报价预计开始 10:00；技师承诺 09:30 到达并按时记录到达，09:30 点击开始被 `SERVICE_TOO_EARLY` 拦截，仍需等待 30 分钟。

定位：`hogulink-api/src/engine.ts:1471–1483`、`:1544`，以及完成时对原开始时间的再次约束。

需要先统一产品规则：

- 指定时间预约保留“不得早于约定时刻开始”。
- 即时单明确预计到达、允许开始和顾客知情规则，不能同时给出两个互相冲突的时间承诺。
- 不论哪一种，结束仍应按实际开始加购买时长校验；不能为消除等待而取消足时保护，也不能悄悄重算冻结金额。

### 4. P2：公开可约时段与实际允许下单的时间范围不一致

**涉及端：顾客、店铺、技师。**

当前指定时间列表统一仅展示未来 72 小时、09:00–21:30 的开始时刻。报价接口则允许未来 30 天，只检查时间距离和资源冲突，没有复用同一营业时间规则。

专项复现：列表没有次日 02:00，但直接按合法参数请求报价、保留并提交后，该预约自动受理，技师确认后成为 `CONFIRMED`。

定位：`hogulink-api/src/engine.ts:518`、`:580–584`。

此处不能简单断言“02:00 必须禁止”：如果店铺支持夜间营业，应开放对应时段；如果实际营业时间只到晚上，接口就不能接受夜间新单。问题是目前没有一个统一、可由店铺管理的营业日历作为依据，列表和下单各用一套规则。

建议：明确店铺营业时段、节假日/停业和人员排班；列表、报价、保留、提交共享同一可约判断。30 天与 72 小时可以分别是预订范围和分页窗口，但不能使顾客无法正常浏览本来允许预订的日期。

### 5. P2：费用一致性仍有三处未闭环

**涉及端：顾客 H5/PC，配置来源为店铺。**

| 场景                                 | 当日专项复现                                                                                             | 建议                                                             |
| ------------------------------------ | -------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------- |
| PC 技师卡片未使用地区交通费          | 服务 7,200、指名 500、原交通 1,000；新宿区改为 4,000 后，卡片仍显示 8,700，未加时段费的正确总价为 11,700 | 卡片、筛选和预约使用同一地区价格函数                             |
| 预算判断前先按旧交通费挑项目         | 当前有 7,700 和 8,100 两项同长度服务，预算 8,000 时却先挑中 8,100 的项目，再排除整名技师                 | 挑选最低价项目时就应用当前地区条件                               |
| H5“总价最低”按不含附加费的基础价排序 | 显示 10,700 的人员排在 8,700 前面                                                                        | 按承诺的总价排序并分页；若坚持基础价策略，展示和排序名称必须一致 |

定位：`hogulink-web/src/components/catalog.tsx:107`、`hogulink-web/src/app/[locale]/page.tsx:72`、`hogulink-api/src/mobile.ts:168`。

这些问题已在当前 `ff41a33` 上重新执行专项复现，不是引用历史截图或旧测试结论。后端最终报价不等于错误卡片金额，但在确认前出现跳价或漏筛会损害用户判断和转化。

## 四、建议的完善顺序

1. **先补安全与超时闭环**：统一安全事件源，补待派单提醒；每个异常有负责人、原截止时间、升级和解除条件。
2. **再统一供给时间规则**：先确定即时单如何开始、店铺何时营业，再统一服务端判断及顾客/技师的时间文案。
3. **再统一费用口径**：同一筛选条件下，“看到的价、排序/预算用的价、下单核对价”使用可解释的一致规则。允许未知时段显示估算，但必须明确估算范围。
4. **把专项复现纳入固定回归**：尤其避免只手写内部记录来证明跨端流程；从正常入口产生数据，再检查另一端的真实待办与结果。

不建议为了填补技师端功能而另加独立接单合同或提现钱包；当前产品是店铺经营、技师履约模式，保持这条主体边界更清晰。
